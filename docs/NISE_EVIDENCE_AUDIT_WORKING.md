**Base commit:** `4652623883e7ec5a60c95795d8013b85610f75c1`

**Purpose:** Evidence-first review before manuscript edits. This is not a claim that the paper is ready for submission.

## Executive finding

**Do not submit the current manuscript yet.** The repository contains useful source code and multiple evaluation artifacts, but the current manuscript combines results from different dataset versions and describes a pipeline that does not exactly match the active implementation. These are evidence/reproducibility problems, not merely writing issues. Do not fix them by choosing whichever number looks best; first establish one canonical experiment and then revise every claim to match it.

## Critical blockers

### B1 — The manuscript's 883-pair benchmark is not established as an independently labeled real-world dataset

**Evidence**
- `backend/jobs/evaluation/buildExact883Dataset.js` builds the 883-pair set from `testCases.json`, `generateExpandedDataset()`, and structured template pairs. It assigns `annotator_1: item.expected` and `annotator_2: item.expected` for baseline pairs and defaults missing annotator labels to `item.expected` for generated pairs.
- `backend/jobs/evaluation/generateExpandedDataset.js` explicitly labels itself a synthetic dataset generator and says its output must not be used for academic publication claims.
- `backend/jobs/evaluation/splits_real/split_report_real.json` reports **N=5,000**, with 2,990 train / 988 validation / 1,022 test. This is a different experiment from the 883-pair split (519 / 166 / 198).
- `backend/jobs/evaluation/iaa_report_real.json` reports κ=0.8454 for 250 items sourced from `testCases_v2_real.json` and the two label files. That is not, by itself, proof that the 883-pair benchmark was independently annotated.

**Impact:** The manuscript currently presents the 883-pair split, κ=0.845, and other benchmark figures as if they form one coherent evaluation protocol. The checked files do not establish that relationship.

**Required repair:** Choose a canonical dataset whose provenance and labels can be documented. If using the 5,000-item RSS-derived corpus, report its actual split sizes (2,990 / 988 / 1,022) and use only its matching test results. If using the 883-pair set, describe its construction honestly and do not call prefilled labels independent annotation. Document the 250-pair human annotation study as a separate reliability study unless a reproducible join proves otherwise.

### B2 — The active event-clustering implementation differs from the manuscript's claimed cascade

**Evidence**
- `backend/jobs/eventEngine.js` evaluates Jaccard, character 3-gram cosine, and EFSA for each recent event, then invokes the LLM if **any** of `passesJaccard || passesCosine || passesEfsa` is true. This is an OR-based candidate trigger, not the paper's sequential “Stage 1 rejects, then Stage 2 EFSA threshold, then Stage 3 LLM” cascade.
- The same file sets `GROQ_MODEL = process.env.GROQ_MODEL || 'openai/gpt-oss-120b'`. The manuscript names Llama 3.1-8B-Instant via Groq. The checked code does not establish which model was active in the measured deployment.
- `backend/utils/textSimilarity.js` implements character n-gram frequency cosine similarity; it is not a transformer embedding model.
- The active `eventEngine.js` file does not invoke the ONNX/SBERT fallback described as Stage 4 in the manuscript. SBERT appears in separate evaluation scripts.

**Impact:** The manuscript's architecture, model identity, and evaluation configuration may not describe the exact implementation used in production.

**Required repair:** Either (a) report the actual committed production path and its actual model/configuration, or (b) clearly identify a separate research/evaluation implementation and prove that its results were generated by that implementation. Do not change production architecture just to fit the manuscript.

### B3 — The 100% LLM-only result is not established as a measured baseline by the current evidence

**Evidence**
- `backend/jobs/evaluation/llm-only-ceiling-results.json` identifies its mode as `extrapolation` and reports a theoretical “perfect ceiling” alongside a conservative estimate.
- `backend/jobs/evaluation/llmOnlyCeiling.js` defaults `useActual = false`; the script explicitly distinguishes an actual all-pairs LLM run from extrapolation.
- `backend/jobs/evaluation/results_v2_final.json` lists an “LLM-Only Ceiling (Exhaustive)” with 100% results, but the checked artifacts do not establish that this exact 198-pair row came from a saved, completed, actual run on the same held-out labels and model.

**Impact:** A theoretical ceiling must not be presented as observed LLM accuracy.

**Required repair:** Locate and preserve the actual per-pair predictions and run configuration, or relabel the row as a theoretical ceiling and exclude it from measured-baseline comparisons.

### B4 — The 82.3% LLM-call reduction is not traceable to a reproducible stage log

**Evidence**
- `results_v2_final.json` says 82.2% calls saved, whereas the manuscript says 82.3%.
- `docs/IEEE_REVIEWER_FINAL_AUDIT.md` computes 82.3% from 35 calls out of 198.
- `backend/jobs/evaluation/runCascadeOnTestSet.js` does not execute the cascade. It reads a result JSON, prints the stage counts as **TBD**, and creates a template requiring the lexical pass count, EFSA pass count, and actual LLM-call count to be filled after a real run.

**Impact:** The rounded percentage and claimed 35-call numerator are not supported by a recorded per-pair stage trace in the checked script/artifacts.

**Required repair:** Run the exact cascade configuration against the canonical held-out set; save predictions, stage decisions, call count, model/version, timestamps, and errors. Recompute call reduction from that output and update all artifacts and manuscript tables from one frozen result file.

### B5 — The SBERT figures in the manuscript refer to a different sample size than the 883/198 headline experiment

**Evidence**
- `backend/jobs/evaluation/sbert-baseline-results_real.json` reports 90.02% accuracy, 95.56% precision, 83.98% recall, F1=89.40%, and 15.07 ms per pair on **N=1,022**.
- `backend/jobs/evaluation/sbert-full-evaluation.json` instead reports the 519 / 166 / 198 split. At threshold 0.50 its held-out test row reports 56.57% accuracy, 100% precision, 13.13% recall, and F1=23.21%; at threshold 0.30 it reports 85.35% accuracy and F1=83.80%.
- `sbertBaseline.js` reads `splits_real/val.json` and `splits_real/test.json`, which correspond to the 5,000-item dataset split, and tunes the threshold on that validation set.

**Impact:** The manuscript's 90% SBERT result is not a like-for-like comparison against the NISE metrics reported on N=198.

**Required repair:** Compare NISE, lexical baselines, and SBERT on the same held-out examples, using thresholds fixed from the same validation protocol. If multiple corpora are reported, separate them into clearly labeled experiments.

### B6 — The 642 ms end-to-end production latency claim needs a durable measurement source

**Evidence**
- The manuscript and audit ledger describe 642 ms as an average pipeline latency from 30-day production telemetry, but the checked `backend/utils/aiTelemetry.js` stores in-memory aggregate LLM-call counters and rolling latency values; it does not establish 30-day persistence or whole-ingestion end-to-end timing.
- `backend/jobs/evaluation/benchmarkLatency.js` measures individual remote LLM completion calls, not the full ingestion pipeline.
- The 650 ms value in the benchmark results is therefore a different measurement boundary from the asserted 642 ms end-to-end mean.

**Impact:** The two values may be legitimate separate measurements, but the current repository evidence does not independently substantiate the stated 30-day end-to-end statistic.

**Required repair:** Find the durable telemetry export and its calculation or remove/qualify the production-wide latency claim. State the measured start/end points, sample count, observation window, and percentile/mean method.

### B7 — Cost values are internally inconsistent

**Evidence**
- The audit ledger calculates a cost per call of $0.00000354 from 42 prompt tokens at $0.05/1M and 18 completion tokens at $0.08/1M.
- That arithmetic implies **$3.54 per million calls** under those token assumptions, while `results_v2_final.json` reports $7.52 per million for NISE and $11.60 per million for the exhaustive LLM baseline.
- The 42/18 token counts are described as assumptions, not a measured distribution from the cited held-out run.

**Required repair:** Use the model and price schedule applicable to the actual experiment; use measured token usage if available. Publish the formula, token assumptions/distribution, and units, and recompute every cost figure consistently.

## Other consistency checks

- The EFSA weights in `backend/utils/efsaEngine.js` are 0.25 / 0.30 / 0.25 / 0.10 / 0.10 and the threshold is 0.22; these are present in code.
- The code's sector list in `buildExact883Dataset.js` contains 15 entries including `cross_sector`; if the manuscript says 14 sectors, explicitly state whether `cross_sector` is a grouping label rather than an additional sector.
- The production default model in `eventEngine.js`, telemetry default model in `aiTelemetry.js`, and manuscript model name differ. Record the actual deployed `GROQ_MODEL` value without exposing any API keys or secrets.
- A precision of 100% on 25 positive predictions with 74 false negatives is a narrow, conservative operating point; report the full confusion matrix, recall, F1, and confidence intervals together. Do not frame it as general high accuracy.
- The manuscript must be compiled and visually inspected; line count is not evidence of a six-page PDF.

## Repair order

1. Freeze the intended research question and identify the single canonical evaluation dataset.
2. Audit provenance and annotation independence; separate real, synthetic, and human-labeled subsets.
3. Run a reproducible held-out comparison of the actual NISE configuration, lexical baselines, and SBERT.
4. Save per-pair predictions and stage-level call traces; calculate metrics and costs from those artifacts.
5. Reconcile active code/model/version against the system diagram and methodology.
6. Rebuild tables/figures and revise the abstract/contributions/limitations to match measured evidence.
7. Verify references, IEEE style, six-page PDF, figure legibility, and submission requirements for the named venue.

## Safety of changes

This audit is on a separate working branch. It does not alter the production pipeline or APIs and does not modify `main`. Manuscript claims should only be changed after the canonical experiment and intended target venue are confirmed.
